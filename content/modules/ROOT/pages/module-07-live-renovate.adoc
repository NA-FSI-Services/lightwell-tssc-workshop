On this page you prove that a bot, not you, updated the Lightwell and Hummingbird pins in git.

Track 3 is application source. This is the third page. xref:module-06-bind-base-deps.adoc[3.2 Bind base and deps] committed the runtime `FROM` and the default Maven property, and left `lightwell-pins.properties` stale. A Renovate CronJob opens one pull request that moves both stale lines. You review that pull request and merge it. A hand-edited commit on the pins file fails the Check.

MintMaker is the name customers use for this bot. This cluster does not install hosted Konflux MintMaker. The term map is xref:appendix-konflux-mapping.adoc[Appendix: Konflux mapping].

== Why this control exists

A trusted software supply chain cannot depend on a person noticing a new Lightwell version. The control is a bot pull request against enterprise git. You merge it the way a developer merges any other pull request. A commit authored by `student` on the pins file is a different control, and the Check rejects it.

The seed is stale on purpose. The bot opens one grouped pull request that moves both lines:

* `commons-lang3=3.14.0.rhlw-00000` becomes the remediated `3.14.0.rhlw-00001` that Nexus already has.
* `hummingbird-digest` moves off the all-zero digest to the dest digest from 1.2.

Merging only the Maven line used to leave a second digest pull request that could not merge, because both lines live in the same file. Leave the file for the bot. The CronJob retries about every 20 minutes.

Lightwell Network catalog bumps are what this bot is seeded to see. A Clearinghouse Premier member version would appear the same way once Nexus, or Artifactory, has metadata the bot can read. During a Premier embargo, you merge the pin. The CVE text and the advisory text stay out of a public pull-request description.

[NOTE]
====
Renovate on a Python application watches `requirements.txt` or `pyproject.toml` for `+rhlw.*` bumps. At a customer, the bot often reads Maven metadata from Artifactory remotes instead of this cluster's Nexus. This Check is a `renovate-bot` pull request on Gitea against the pins file.
====

In a customer engagement the bot runs against GitHub or GitLab. Here the git is Gitea. Red Hat operates the workshop CronJob on this cluster. You merge the pull request.

== Your change

In Gitea, open `lw-student/spring-boot-lw-poc` and then *Pull Requests*. The scored pull request is authored by `renovate-bot`. The files include `lightwell-pins.properties`. Both seed values, `rhlw-00000` and the all-zero digest, move in that one pull request. Review it, then merge it in the Gitea UI.

The capture is that pull request after the merge. The comment is from `renovate-bot`. The table shows both the Hummingbird digest and `commons-lang3`. The merge on the page is yours. The pin commit is the bot's.

If the pull request is not there yet, wait for the next CronJob and read the Job logs in namespace `renovate`. The Maven bump appears once the Nexus remotes are up. The dest Docker bump needs the 1.2 mirror. A student commit that edits the pins file fails the Check.

After the merge, refresh the clone from 3.2. `git log -1` is your merge commit. Success is a pins file that has moved off `rhlw-00000` and the all-zero digest, and a `renovate-bot` commit on that file. The second `git log` lists commits for `lightwell-pins.properties`. The newest of those is `renovate-bot`.

.Refresh the clone
[source,bash,role=execute]
----
cd /tmp/spring-boot-lw-poc
git fetch origin
git checkout main
git pull --ff-only origin main
git log -1 --format='%an %ae %s'
git log --format='%h %an %ae %s' -- lightwell-pins.properties
cat lightwell-pins.properties
----
