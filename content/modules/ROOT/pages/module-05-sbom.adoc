= Module 5: SBOM generation and analysis with RHTPA (RHDA)
:source-highlighter: rouge
:toc:
:toclevels: 2

Lightwell Network artifacts travel with supply-chain metadata; your *application* build should too. Every Lightwell-distributed package is built with *Supply-chain Levels for Software Artifacts (SLSA)* Level 3 integrity and signed; Maven packages include CycloneDX *Software Bills of Materials (SBOMs)* and *Vulnerability Exploitability eXchange (VEX)* advisories (Python wheels use *Software Package Data Exchange (SPDX)*). In this module you generate a *CycloneDX* SBOM from the Spring Boot PoC with `syft`, ingest it into *Red Hat Trusted Profile Analyzer (RHTPA)* (also called *TPA*), and learn how *Red Hat Dependency Analytics (RHDA)* is the laptop IDE shift-left client of the same intelligence, without installing an IDE in Showroom.

Customers submit *dependency manifests* (for example `pom.xml`) and SBOMs for program workflows—not proprietary application source code. Application source stays in the customer environment.

== Learning objectives

By the end of this module, you will be able to:

* Produce a CycloneDX JSON SBOM from the Spring Boot PoC (JAR or `target/` tree) with `syft`
* Locate RHTPA upload/browse guidance from ConfigMap `rhtpa-ingestion-info`
* Ingest the SBOM via REST API (`POST /api/v3/sbom`) from Showroom, then browse it in the TPA UI
* Explain how *VEX* / OSV feeds help CI scanners recognize Lightwell-patched CVEs
* Explain RHDA vs RHTPA roles and when instructors demo RHDA on a laptop

== Prerequisites

* xref:module-02-maven.adoc[Module 2] — Maven `settings.xml` / Nexus
* xref:module-04-osv.adoc[Module 4] — remediated pins context (optional but recommended); end-of-module SSO check
* Chart `keycloak` Healthy/Synced (namespace `sso`) — IdP at `https://sso.<domain>/realms/tpa`
* Chart `rhtpa` Healthy/Synced when you need a live UI (namespace `trusted-profile-analyzer`)

== Exercise 0: Confirm Keycloak *single sign-on (SSO)* for TPA

GitOps imports the `tpa` realm with Trustify **chicken-*** roles and **read|create|delete:document** client scopes. Learners do *not* create roles in the Keycloak Admin Console.

. Recover workshop username, password, and OIDC issuer from userinfo:
+
[source,bash,role=execute]
----
oc -n sso get configmap demo-userinfo-keycloak \
  -o jsonpath='issuer={.data.oidc_issuer}{"\n"}user={.data.workshop_username}{"\n"}pass={.data.workshop_password}{"\n"}roles={.data.trustify_roles}{"\n"}'
----
+
Expect `issuer=…/realms/tpa`, `user=tpa-user`, and a non-empty `pass=` value (chart default is `workshop-tpa-user-changeme` unless RHDP overrode it).

. Discover the **browser URL you will open to sign in** — that is the **TPA UI Route**, not the Keycloak `/admin/` console:
+
[source,bash,role=execute]
----
# Preferred: RHTPA ingestion userinfo (same host learners use in Exercise 3)
oc -n trusted-profile-analyzer get configmap rhtpa-ingestion-info \
  -o jsonpath='tpa_ui={.data.server_url}{"\n"}'

# Equivalent Route (host only — prefix with https://)
oc -n trusted-profile-analyzer get route -o custom-columns=NAME:.metadata.name,HOST:.spec.host
----
+
Open `tpa_ui` / `https://<HOST>` in your browser. Keycloak redirects you to the IdP; the address bar must contain **`/realms/tpa/`** (page title like “Sign in to tpa”). Sign in with `user` / `pass` from the previous step. You will repeat this in Exercise 3 when uploading the SBOM.

. Optional — confirm the IdP issuer and SSO Route separately (diagnostics only; do **not** log in at `/admin/`):
+
[source,bash,role=execute]
----
oc -n sso get route sso -o jsonpath='sso_host={.spec.host}{"\n"}'
# Issuer must end with /realms/tpa (already printed as issuer= above)
echo "OIDC discovery: $(oc -n sso get configmap demo-userinfo-keycloak -o jsonpath='{.data.oidc_issuer}')/.well-known/openid-configuration"
----

[IMPORTANT]
====
Do **not** open `https://sso.<domain>/admin/` for Module 5. That is the Keycloak *Admin Console* (`master` realm). Workshop user `tpa-user` exists only in realm **`tpa`**. Starting from the TPA UI Route forces the correct *OpenID Connect (OIDC)* redirect.
====

image::module-05-tpa-sso-signin.png[Keycloak tpa realm sign-in for RHTPA,width=700,link=self,window=blank]

Confirm the page shows realm branding **TPA** (not the Keycloak Admin Console). Username is typically prefilled or entered as `tpa-user`; leave the password blank until you paste `pass=` from the ConfigMap command above, then **Sign In**.

[TIP]
====
*Fresh catalog / bootstrap claims:* Job `rhtpa-oidc-wait` in `trusted-profile-analyzer` waits for
`https://sso.<domain>/realms/tpa/.well-known/openid-configuration` and rolls Deployment `server`
only if it is not Ready — confirm with `oc -n trusted-profile-analyzer get job rhtpa-oidc-wait`.

*Long-lived claims* where Keycloak was synced *before* Trustify roles landed in Git: recreate the
Keycloak pod after ArgoCD syncs `charts/components/keycloak`
(`oc -n sso delete pod -l app=keycloak`). `start-dev` has no *PersistentVolumeClaim (PVC)*, so
`--import-realm` reloads `tpa` with chicken roles and document scopes. Then restart RHTPA so it
reloads *JSON Web Key Set (JWKS)* material:
`oc -n trusted-profile-analyzer rollout restart deploy/server`
(scale to `0` then `1` if the server PVC leaves pods CrashLoopBackOff).
====

=== Verify

* The first command outputs `issuer=…/realms/tpa`, `user=tpa-user`, and a non-empty `pass=` value.
* Navigating to the TPA UI URL redirects to a Keycloak page whose address bar contains `/realms/tpa/` (not `/admin/`).
* After signing in with the `user` / `pass` from the ConfigMap, the browser returns to the TPA application home screen (not an error or the Keycloak Admin Console).
* (Optional diagnostics) The OIDC discovery URL printed in step 3 returns a valid JSON document when opened in a browser or fetched with `curl`.

== Roles: RHTPA vs RHDA

[cols="1,2,2",options="header"]
|===
|Component |Role in this workshop |Where it runs

|*RHTPA*
|SBOM and advisory *system of record*; CycloneDX ingest; VEX/advisory importers
|Cluster (`charts/components/rhtpa`)

|*syft*
|Generate CycloneDX from image or directory/JAR
|Showroom terminal, pipeline Task `syft-sbom-rhtpa`, or laptop

|*RHDA*
|IDE client (wavy underlines on `pom.xml`) consuming TPA / Exhort intelligence
|Instructor or demo *laptop* only — not in Showroom
|===

OSV feeds and *VEX* metadata published with Lightwell content let code-scanning tools in *continuous integration / continuous delivery (CI/CD)* recognize that a CVE has been remediated via a `.rhlw-*` pin—so pipelines do not keep flagging the issue as unpatched after you adopt Remediated.

Full author notes: `docs/rhda-rhtpa-shift-left.md`. Showroom appendix: xref:rhda-shift-left.adoc[RHDA shift-left].

== Exercise 1: Read RHTPA ingestion hints

. Confirm the ingestion ConfigMap (present when `rhtpa` is synced):
+
[source,bash,role=execute]
----
oc -n trusted-profile-analyzer get configmap rhtpa-ingestion-info -o yaml
----

. Extract the server URL and supported CycloneDX version:
+
[source,bash,role=execute]
----
oc -n trusted-profile-analyzer get configmap rhtpa-ingestion-info \
  -o jsonpath='{.data.server_url}{"\n"}{.data.supported_cyclonedx_version}{"\n"}{.data.upload_hint}{"\n"}'
----

. Optional: list TPA-related Routes:
+
[source,bash,role=execute]
----
oc -n trusted-profile-analyzer get routes
----

If the namespace is not ready yet, continue with SBOM *generation* locally; upload when the UI Route is Healthy.

=== Verify

* The `rhtpa-ingestion-info` ConfigMap is present in namespace `trusted-profile-analyzer` (no `Error from server (NotFound)` message).
* The `server_url` field starts with `https://` and resolves to the TPA application host.
* The `supported_cyclonedx_version` field is non-empty (for example `1.4` or higher).
* (Optional) `oc -n trusted-profile-analyzer get routes` lists at least one route whose host matches the `server_url` printed above.

== Exercise 2: Generate CycloneDX with `syft`

Build the PoC, then scan the artifact or `target/` directory.

. From the Spring Boot PoC app directory (Gitea clone from Module 3 scaffold):
+
[source,bash,role=execute]
----
cd /tmp/spring-boot-lw-poc

: "${LIGHTWELL_NEXUS_URL:=https://$(oc -n lightwell-repo get route nexus -o jsonpath='{.spec.host}')}"
: "${MVN_LOCAL:=-Dmaven.repo.local=/tmp/m2}"

mvn $MVN_LOCAL -s settings.xml -Plightwell-validated package -DskipTests \
  > /tmp/mvn-package-m4-validated.log 2>&1

grep -E 'BUILD SUCCESS|BUILD FAILURE' /tmp/mvn-package-m4-validated.log
ls -la target/*.jar
----

. Generate CycloneDX JSON with `syft` (preferred — matches pipeline Task `syft-sbom-rhtpa`):
+
[NOTE]
====
Stock Showroom terminals often ship *without* `syft` on `PATH`, and without `podman` / `docker`.
Install a pinned binary under `/tmp` (writable home), then use that `syft` for this exercise:
====
+
[source,bash,role=execute]
----
# Install syft once per terminal session (Showroom-friendly; uses /tmp)
mkdir -p /tmp/bin
curl -sSfL https://raw.githubusercontent.com/anchore/syft/main/install.sh \
  | sh -s -- -b /tmp/bin v1.18.1
export PATH="/tmp/bin:$PATH"
syft version
----
+
[source,bash,role=execute]
----
# If syft is already on PATH (or after the install above):
syft packages "dir:target" -o cyclonedx-json > sbom.cyclonedx.json

# Or scan the executable/boot JAR explicitly:
# syft packages "file:target/spring-boot-lw-poc-0.1.0-SNAPSHOT.jar" -o cyclonedx-json > sbom.cyclonedx.json

ls -la sbom.cyclonedx.json
head -c 400 sbom.cyclonedx.json; echo
----

. Optional — if you have `podman` or `docker` on a laptop (not typical in Showroom), run the published image (same family as the Tekton Task):
+
[source,bash,role=execute]
----
podman run --rm -v "$PWD:/work:z" -w /work \
  ghcr.io/anchore/syft:v1.18.1 \
  packages "dir:target" -o cyclonedx-json > sbom.cyclonedx.json
----
+
(`docker` works the same way if that is your runtime.)

. Sanity-check the document:
+
[source,bash,role=execute]
----
jq '{bomFormat, specVersion, components:(.components|length)}' sbom.cyclonedx.json
----
+
Expect `bomFormat` of `CycloneDX` and a non-zero `components` count.

[TIP]
====
Seeded Lightwell artifact SBOMs also exist under the Nexus raw repo path `sbom/java/...` (chart `lightwell-repo`). Those demonstrate *component* metadata; this exercise focuses on the *application* SBOM from your build.
====

=== Verify

* `syft version` printed a version string (for example `syft 1.18.1`) without errors.
* `ls -la sbom.cyclonedx.json` shows the file exists and has a size greater than zero.
* The `mvn … package` build reported `BUILD SUCCESS` and `ls -la target/*.jar` lists at least one JAR file.
* Running `jq '{bomFormat, specVersion, components:(.components|length)}' sbom.cyclonedx.json` outputs `"bomFormat": "CycloneDX"` and a non-zero `components` count (typically several dozen for a Spring Boot project).

== Exercise 3: Ingest and browse in RHTPA

Ingest from the Showroom terminal with the Trustify REST API (no browser file picker). Then open the TPA UI only to browse what you uploaded.

=== Ingest via API (Showroom)

Trustify 3 accepts:

[source,text]
----
POST {RHTPA_BASE}/api/v3/sbom
Content-Type: application/octet-stream
Authorization: Bearer <OIDC access token>
----

. Stay in the Exercise 2 workspace that contains `sbom.cyclonedx.json` (or `cd` back to it). Confirm the file is present:
+
[source,bash,role=execute]
----
test -f sbom.cyclonedx.json && ls -la sbom.cyclonedx.json
----

. Recover OIDC issuer, workshop credentials, CLI client secret, and TPA base URL from the cluster, then POST the SBOM:
+
[source,bash,role=execute]
----
export OIDC_ISSUER="$(oc -n sso get configmap demo-userinfo-keycloak \
  -o jsonpath='{.data.oidc_issuer}')"
export RHTPA_URL="$(oc -n trusted-profile-analyzer get configmap rhtpa-ingestion-info \
  -o jsonpath='{.data.server_url}')"
export TPA_USER="$(oc -n sso get configmap demo-userinfo-keycloak \
  -o jsonpath='{.data.workshop_username}')"
export TPA_PASS="$(oc -n sso get configmap demo-userinfo-keycloak \
  -o jsonpath='{.data.workshop_password}')"
export CLI_SECRET="$(oc -n trusted-profile-analyzer get secret tpa-realm-cli-clients \
  -o jsonpath='{.data.cli}' | base64 -d)"

TOKEN="$(curl -sk -X POST "${OIDC_ISSUER}/protocol/openid-connect/token" \
  -d grant_type=password \
  -d client_id=cli \
  -d client_secret="${CLI_SECRET}" \
  -d username="${TPA_USER}" \
  -d password="${TPA_PASS}" \
  -d scope=openid \
  | jq -r .access_token)"

curl -sk -X POST \
  -H "Authorization: Bearer ${TOKEN}" \
  -H "Content-Type: application/octet-stream" \
  --data-binary @sbom.cyclonedx.json \
  -w '\nHTTP %{http_code}\n' \
  "${RHTPA_URL%/}/api/v3/sbom"
----

. Confirm HTTP **201** (or another success code) and a small JSON body with an SBOM `id`.
+
Stock `syft` often emits CycloneDX `specVersion` 1.5/1.6; that is expected even when ingestion metadata says `1.4+`.
Workshop tokens must include Trustify document scopes (`create:document`, …); the `cli` client and `tpa-user` receive those from the Keycloak realm import. Pipeline Task `syft-sbom-rhtpa` (Module 6) uses the same `POST /api/v3/sbom` pattern. Do not commit tokens or passwords.

=== Browse in the TPA UI

. Open the TPA UI (`server_url` / Route host from Exercise 0 / Exercise 1). Re-print if needed:
+
[source,bash,role=execute]
----
oc -n trusted-profile-analyzer get configmap rhtpa-ingestion-info \
  -o jsonpath='{.data.server_url}{"\n"}'
----
+
You can also use the Showroom **RHTPA** tab.

. Sign in when Keycloak redirects you. Re-print credentials if you closed the terminal:
+
[source,bash,role=execute]
----
oc -n sso get configmap demo-userinfo-keycloak \
  -o jsonpath='user={.data.workshop_username}{"\n"}pass={.data.workshop_password}{"\n"}'
----
+
Confirm the browser URL contains `/realms/tpa/` (not `/admin/`). After a successful sign-in you return to TPA.

. Browse the ingested SBOM: locate packages such as `commons-lang3` and Spring Boot starters. Tie findings mentally to Module 4 remediated pins (`.rhlw-*`) when a vulnerable coordinate appears.

image::module-05-rhtpa-sbom-ui.png[RHTPA All SBOMs after CycloneDX ingest,width=700,link=self,window=blank]

Confirm the list shows your ingested SBOM (often named `target` when generated from `dir:target`) with a `type=cyclonedx` label. Open the name link to browse packages such as `commons-lang3` and Spring Boot starters.

=== Aside: Upload through the TPA UI (laptop)

Use this only when `sbom.cyclonedx.json` is on the same machine as the browser (for example a laptop clone + local `syft`). The TPA *file picker* cannot see files inside the Showroom `/terminal/` filesystem.

. Open the TPA UI and sign in (same steps as <<browse-tpa-ui>>).
. Choose SBOMs / upload (labels vary slightly by TPA version) and select `sbom.cyclonedx.json`.
. Confirm the SBOM appears in the list, then continue with the browse steps above.

=== Verify

* The `curl` POST returned HTTP **201** and a JSON response body containing an `id` field (a UUID or numeric identifier for the ingested SBOM).
* The TPA UI SBOM list shows a new entry labelled `target` (or the JAR name) with `type=cyclonedx`.
* Clicking the SBOM name in the UI opens a package list that includes Spring Boot starters and `commons-lang3` (or other PoC dependencies).
* No `401 Unauthorized` or `403 Forbidden` response was received; if one appears, re-run the token exchange step (step 2 of the Ingest via API section) and re-POST.

== Module summary

**What you accomplished**

* Confirmed Keycloak `tpa` SSO credentials and Trustify authorization scopes/roles
* Generated a CycloneDX SBOM from the Spring Boot PoC with `syft`
* Located RHTPA ingestion metadata and ingested/browsed the SBOM (UI and/or API)
* Distinguished RHTPA (cluster system of record) from RHDA (laptop shift-left)

**Key takeaways**

* Prefer CycloneDX JSON from `syft` for this workshop (Maven Lightwell packages also ship CycloneDX + VEX; Python uses SPDX)
* TPA UI/API authorization comes from the workshop Keycloak realm (`chicken-*` + `*:document` scopes)—not from ad-hoc Admin Console edits
* OSV/VEX help scanners treat Lightwell remediations as fixed—not still-open CVEs
* Pipeline Task `syft-sbom-rhtpa` automates the same generate-and-API-upload path in Module 6 (`POST /api/v3/sbom`)
* RHDA is optional on a laptop; learners do not need an IDE inside Showroom; do not upload proprietary app source to Red Hat for LWN
