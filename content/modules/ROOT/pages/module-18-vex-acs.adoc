On this page you prove two closing facts. Trusted Profile Analyzer shows the Track 2 library CVE as remediated by the Lightwell pin. The pipeline's Advanced Cluster Security check is actually running.

Track 7 is continuous compliance. This is the second page. You download the GAV-bound CycloneDX and the scored OSV for the pin you set on xref:module-04-remediated-pin.adoc[2.2 Remediated pin], ingest them, and write a blast-radius report whose remediation token is `via-lightwell-pin`. Hummingbird and Red Hat CSAF are the operating-system layer. They are a callout, not the Check. The live CSAF importer stays off.

Task `acs-image-check` has to come back `passed` or `failed`. A `skipped` result fails the Check. Admission was xref:module-15-gitops-admission.adoc[6.1 GitOps + admission]. ACS is not that gate.

== Why this control exists

Continuous compliance means the system of record can say why the library CVE is closed, and the pipeline scan is on. The library statement is GAV-bound Lightwell Network metadata: OSV `LW-DEMO-0002` plus the Maven CycloneDX classifier for `commons-lang3` at `3.14.0.rhlw-00001`. Quoting a RHEL or Hummingbird CSAF advisory for that library CVE over-claims. The operating-system advisory and the library advisory are different layers.

Scanners and Trusted Profile Analyzer recognize the pin only after you ingest that metadata. Provision does not pre-ingest it. `fail-on-skipped: "true"` on `acs-image-check` is what makes a soft-skip fail the task. `passed` and `failed` both prove the control ran.

A Clearinghouse Premier member advisory ingests the same way. The report still says the remediation is the Lightwell pin, including a member version. It does not say the upstream line was fixed, and it does not say a Hummingbird CSAF closed a library CVE. The public OSV on this Check is the post-disclosure Network state. During a Premier embargo, that advisory would stay inside the member set, off public scanner feeds, until disclosure. ACS can still scan the image.

You pull the public Network files from the enterprise proxy and put them in the system of record. Red Hat CSAF remains the other layer.

== Your change

Download the Maven classifier `cdx` from the userinfo URL on Nexus Remediated, and POST it to `/api/v3/sbom`. The companion `-vex.json` classifier is OpenVEX. Trusted Profile Analyzer does not accept OpenVEX as an SBOM, and it does not accept OpenVEX on `/api/v3/advisory`. That path takes CSAF, a CVE record, or OSV. Ingest the scored OSV document, `scored_vex_osv`, file `LW-DEMO-0002.json`. Leave CSAF unscraped. Leave OpenVEX off `/api/v3/sbom`.

The token request is the same client you used on 7.1. Success is an HTTP success code for the CycloneDX POST and an HTTP success code for the OSV POST. `live_csaf_gate` stays false.

.Download and ingest the GAV documents
[source,bash,role=execute]
----
CDX_URL="$(oc -n lightwell-repo get configmap demo-userinfo-lightwell-repo -o jsonpath='{.data.scored_vex_maven_cdx}')"
OSV_URL="$(oc -n lightwell-repo get configmap demo-userinfo-lightwell-repo -o jsonpath='{.data.scored_vex_osv}')"
curl -fsSL -o ~/commons-lang3-cdx.json "${CDX_URL}"
curl -fsSL -o ~/LW-DEMO-0002.json "${OSV_URL}"
export OIDC_ISSUER="$(oc -n sso get configmap demo-userinfo-keycloak -o jsonpath='{.data.oidc_issuer}')"
export RHTPA_URL="$(oc -n trusted-profile-analyzer get configmap rhtpa-ingestion-info -o jsonpath='{.data.server_url}')"
export TPA_USER="$(oc -n sso get configmap demo-userinfo-keycloak -o jsonpath='{.data.workshop_username}')"
: "${TPA_PASS:=$(oc -n sso get configmap demo-userinfo-keycloak -o jsonpath='{.data.workshop_password}')}"
export CLI_SECRET="$(oc -n trusted-profile-analyzer get secret tpa-realm-cli-clients -o jsonpath='{.data.cli}' | base64 -d)"
TOKEN="$(curl -sk -X POST "${OIDC_ISSUER}/protocol/openid-connect/token" \
  -d grant_type=password -d client_id=cli -d client_secret="${CLI_SECRET}" \
  -d username="${TPA_USER}" -d password="${TPA_PASS}" -d scope=openid \
  | jq -r .access_token)"
curl -sk -X POST -H "Authorization: Bearer ${TOKEN}" \
  -H "Content-Type: application/octet-stream" \
  --data-binary @"${HOME}/commons-lang3-cdx.json" \
  -w '\nCDX HTTP %{http_code}\n' \
  "${RHTPA_URL%/}/api/v3/sbom"
curl -sk -X POST -H "Authorization: Bearer ${TOKEN}" \
  -H "Content-Type: application/octet-stream" \
  --data-binary @"${HOME}/LW-DEMO-0002.json" \
  -w '\nOSV HTTP %{http_code}\n' \
  "${RHTPA_URL%/}/api/v3/advisory"
----

== Key takeaways

* The library CVE is remediated because the application pins `3.14.0.rhlw-00001`, and the system of record has the OSV that says so.
* A Hummingbird or RHEL CSAF advisory is the operating-system layer. It does not close this library CVE.
* A Premier member advisory uses the same ingest. During an embargo that metadata stays off public feeds.
* ACS on the pipeline is a scan of the image. Unsigned deny remains the 6.1 admission gate.
