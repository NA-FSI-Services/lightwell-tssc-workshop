= 1.2 Mirror into the trust boundary
:source-highlighter: rouge
:toc:
:toclevels: 2

1.1 verified the *published* Hummingbird pin. This cluster did *not* pre-load that image. Dest Docker repo `hummingbird-mirror` starts empty so *you* run `oc-mirror`.

In this module you finish the incomplete `ImageSetConfiguration`, start the learner Job from ConfigMap `oc-mirror-tooling`, and `cosign verify` the *internal* digest you record — not only the public digest from xref:module-01-hummingbird-verify.adoc[1.1].

== How this serves TSSC

TSSC’s trust boundary is *inside* the enterprise, not `registry.access.redhat.com` at build time. Builds, GitOps, and admission must pull a dest digest you can still verify. 1.2 is the observation that signatures and the image travel together when you author the ImageSet and run oc-mirror yourself.

You learn `ImageSetConfiguration` and dest coordinates because that file is what a customer bastion runs. Leaving dest empty until you run the Job is the skill; a pre-mirrored claim would only be a screenshot.

Lightwell Network and Clearinghouse Premier consume *Maven/PyPI* through the artifact manager (Track 2), not Docker `additionalImages`. Premier does not change oc-mirror. Both Lightwell models still *depend* on this dest Hummingbird: Track 3 binds `FROM` to the internal digest you record here.

== Learning objectives

By the end of this module, you will be able to:

* Observe TSSC’s trust-boundary control: the published Hummingbird image, signatures, and SBOM land on an internal dest you can `cosign verify`
* Replace `REPLACE_ME_HUMMINGBIRD_PULLSPEC` with the live digest pin from userinfo (not the worked-example UBI)
* Start Job `oc-mirror-learner` from `oc-mirror-tooling` (not a provision Job) and record the *internal* dest digest
* Explain that Lightwell (Network or Premier) libraries are a different input path (Nexus), while this dest digest is the runtime `FROM` later tracks bind

== Why dest is empty

An enterprise DMZ host runs `oc-mirror`; this Showroom is the in-cluster stand-in. If provision mirrored Hummingbird for you, the Check would be a screenshot of a finished cluster — not a skill.

== Your change: ImageSet

.Copy the live pin into a note (same key as 1.1)
[source,bash,role=execute]
----
oc -n lightwell-repo get configmap demo-userinfo-lightwell-repo \
  -o jsonpath='{.data.hummingbird_source_pullspec}{"\n"}'
----

Edit ConfigMap `imageset-configuration` in namespace `lightwell-repo` so `mirror.additionalImages[0].name` is that pull spec (digest, not `:latest`). The seed looks like:

[source,yaml]
----
kind: ImageSetConfiguration
apiVersion: mirror.openshift.io/v2alpha1
mirror:
  additionalImages:
    - name: REPLACE_ME_HUMMINGBIRD_PULLSPEC
----

Use `oc -n lightwell-repo edit configmap imageset-configuration` and change only that `name:` line. Do not copy `example-imageset.yaml` over the scored key.

The Job does *not* pass `--remove-signatures`. oc-mirror v2 still cannot land OCI referrers on this Nexus Docker dest, so the Job copies the image first, then copies tag-based signatures (`.sig` / `.att` / `.sbom`) with `cosign copy`. Do not add a flag that strips signatures.

== Run oc-mirror (learner Job)

`oc-mirror` is on Showroom `PATH`, but the scored run is the in-cluster Job so dest credentials and the workspace PVC are already wired.

.Delete a previous attempt if the Job name already exists, then create from tooling
[source,bash,role=execute]
----
oc -n lightwell-repo delete job oc-mirror-learner --ignore-not-found
oc -n lightwell-repo get configmap oc-mirror-tooling \
  -o jsonpath='{.data.job\.yaml}' | oc create -f -
----

.Wait for completion (mirror + signatures can take several minutes)
[source,bash,role=execute]
----
oc -n lightwell-repo wait --for=condition=complete job/oc-mirror-learner --timeout=20m
----

.Read oc-mirror logs for the dest image, then the signature-copy container
[source,bash,role=execute]
----
oc -n lightwell-repo logs job/oc-mirror-learner -c oc-mirror
oc -n lightwell-repo logs job/oc-mirror-learner -c copy-signatures
----

Record the *dest* digest from those logs (or dest registry metadata). Do not reuse only the 1.1 published digest as proof that dest is populated.

== Check: internal `cosign verify`

Build a dest pull spec from:

* `dest_registry_host` (userinfo)
* image path `hi/openjdk` (not the Nexus Docker repo name `dest_registry_repo` / `hummingbird-mirror`)
* the dest digest *you recorded from the Job*

Or copy the `DEST_PULLSPEC=` line from the `copy-signatures` container log.

Then verify with the same Red Hat Hardened Images public key as 1.1. Dest TLS is lab-internal; allow an insecure registry if `cosign` requires it:

[source,bash]
----
# Stub — fill DEST_PULLSPEC from Job logs + dest_registry_host. Not the worked UBI example.
export DEST_PULLSPEC='REPLACE_ME_DEST_PULLSPEC'
cosign verify \
  --allow-insecure-registry \
  --key https://security.access.redhat.com/data/63405576.txt \
  --insecure-ignore-tlog \
  "${DEST_PULLSPEC}"
----

== Key takeaways

* TSSC requires the signed base *inside* the trust boundary. Mirror is a learner skill, not a finished cluster.
* Internal verify is a different Check from published verify.
* Signatures stay with the image because the Job copies them onto dest (Nexus stores the tag protocol, not OCI referrers).
* Lightwell Network / Clearinghouse Premier do not replace this dest; Track 3 `FROM` uses it.
