= 4.3 Build NetworkPolicy
:source-highlighter: rouge
:toc:
:toclevels: 2

On this page you prove that pods in the build namespace can reach only the in-cluster services the hermetic build needs.

Track 4 is the hermetic build. This is the third page. xref:module-08-forbid-list.adoc[4.1 Source forbid-list] and xref:module-09-prefetch.adoc[4.2 Prefetch (Hermeto mapping)] removed the public fetches from source and filled a local Maven cache. NetworkPolicy `build-egress` on `lw-poc-build` is still seeded to allow every egress. You replace that with a deny-by-default policy that allows DNS, the internal registry, Nexus, in-cluster Gitea, and the Kubernetes API. xref:module-11-build-sbom.adoc[4.4 Build and SBOM] clones and runs `oc start-build`, so those last two allows have to be present. A policy that also allows a public registry host, or the worked-example address `8.8.8.8`, fails the Check.

The same policy does not belong on `lw-poc-staging` or `lw-poc-prod`. NetworkPolicy `app-operate` on those namespaces stays the operate policy. Track 6 grades that separately.

== Why this control exists

Source grep is the first gate. The network is the one that still holds after someone skips a file. Once you tighten `build-egress`, Maven Central, public registries, and the Nexus Route fail from `lw-poc-build`. Lightwell Network GAVs use the in-cluster Nexus Service. The git clone uses the in-cluster Gitea URL.

OpenShift's OVN matcher sees the pod port after DNAT, not the Service port you might read from `oc get svc`. A rule for Service port `443` does not allow a pod that listens on `8443`. A missing allow for Gitea, Nexus, or Red Hat Trusted Artifact Signer breaks 4.4 and 5.1. An extra public CIDR undoes the control.

Lightwell Clearinghouse Premier does not need `packages.redhat.com` on this allow-list. The member artifacts are already in the proxy you allow.

[NOTE]
====
The allow-list below is longer than the four boxes in the left column. DNS, the registry, Gitea, and Nexus are the hermetic core. The Kubernetes API, Advanced Cluster Security, Trusted Artifact Signer, and Trusted Profile Analyzer are on the list so later pipeline tasks can run. `registry.redhat.io` stays off the list.
====

In a customer engagement, CI namespaces are isolated from the namespaces where the application runs. You keep those two policies separate.

== Learning objectives

By the end of this module, you will be able to:

* Replace allow-all egress on `build-egress` with the in-cluster allow-list
* Name each allowed namespace and the pod port OVN will match
* Confirm the tightened policy is live on `lw-poc-build` only
* Explain that Network and Premier remediations keep resolving through Nexus port `8081`

== The seed and the allow-list

Success of the reads is a NetworkPolicy whose egress is still allow-all, a userinfo ConfigMap of hints, and an example policy you will not apply.

.Read the seed and the hints
[source,bash,role=execute]
----
oc -n lw-poc-build get networkpolicy build-egress -o yaml
oc -n lw-poc-build get configmap demo-userinfo-networkpolicy -o yaml
oc -n lw-poc-build get configmap networkpolicy-docs \
  -o jsonpath='{.data.example-hermetic-egress\.yaml}'
----

The block below is a policy with the wrong name, the wrong namespace, and a public DNS address. A paste of that object fails the Check.

[source,yaml]
----
# Worked example ONLY — wrong name, wrong namespace, public DNS.
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: example-hermetic-egress
  namespace: example-build-ns
spec:
  podSelector: {}
  policyTypes: [Egress]
  egress:
    - to:
        - ipBlock:
            cidr: 8.8.8.8/32
----

The allow-list comes from the userinfo keys. The only addresses you discover yourself are the Kubernetes API ClusterIP and its endpoint IPs. Everything else is a `namespaceSelector` plus the pod port.

* Namespace `openshift-dns`, UDP and TCP port `5353`.
* Namespace `openshift-image-registry`, TCP port `5000`.
* Namespace `lightwell-repo`, Nexus HTTP port `8081` and the Docker dest port `5000`.
* Namespace `gitea`, TCP port `3000`. That is the in-cluster clone, not the Gitea Route.
* The Kubernetes API: Service `default/kubernetes` ClusterIP, TCP `443`, plus the endpoint IPs, TCP `6443`. Those endpoints are hostNetwork control-plane nodes. A `namespaceSelector` of `default` does not match them, so they are `ipBlock` entries of `/32`.
* Namespace `stackrox`, TCP `8443`. Central's Service port is `443` and the pod port is `8443`. A rule for port `443` does not allow it.
* Namespace `trusted-artifact-signer`: TCP `8080` for TUF, `5555` for Fulcio HTTP, `5554` for Fulcio gRPC, and `3000` for Rekor.
* Namespace `trusted-profile-analyzer`, TCP `8080`. The TPA Service port is `443` and the pod port is `8080`.

Each arrow starts at NetworkPolicy `build-egress` and ends on one of those destinations.

The API addresses differ per cluster. Success is one ClusterIP line and one endpoints line.

.Discover the API addresses
[source,bash,role=execute]
----
oc -n default get svc kubernetes -o jsonpath='clusterIP={.spec.clusterIP} port={.spec.ports[0].port}{"\n"}'
oc -n default get endpoints kubernetes -o jsonpath='{.subsets[*].addresses[*].ip}{" "}{.subsets[*].ports[*].port}{"\n"}'
----

== Your change

Replace the seed `egress: [ {} ]` with deny-by-default plus the destinations above. Use a `namespaceSelector` for those namespaces, and match the pod ports from userinfo. Add an `ipBlock` of `/32` for the kube API ClusterIP and for each endpoint IP. Leave `registry.redhat.io` and any public CIDR off the policy. A `namespaceSelector` of `openshift-ingress` does not make Route hostnames work: those names resolve to the ingress VIP, and that selector does not match the VIP. After this page, 4.4 uses in-cluster Gitea (`student_repo_internal_url`) and Nexus (`nexus_internal_url`). Pipeline tasks that talk to ACS, keyless signing, or TPA need the stackrox, Trusted Artifact Signer, and TPA pod ports. Service port `80` or `443` is not enough.

Success is a live `build-egress` that is no longer allow-all, and an `app-operate` policy that is still the operate seed.

.Replace build-egress
[source,bash,role=execute]
----
oc -n lw-poc-build get networkpolicy build-egress -o yaml
# edit in place or oc apply a file you authored — not example-hermetic-egress.yaml
oc -n lw-poc-staging get networkpolicy app-operate
----

== Check

The pass is the live object. `build-egress` exists in `lw-poc-build`, is not allow-all egress, and includes DNS, the registry, and Nexus. The extra allows for Gitea, the kube API, stackrox port `8443`, and the Trusted Artifact Signer pod ports are expected, so 4.4 and 5.1 can run. The policy is not copied to `lw-poc-staging`. `app-operate` on staging and prod is still the operate seed.

After this tighten, a PipelineRun that still clones the Gitea HTTPS Route, or that resolves Maven from Central, hangs or fails. That is the control. It is not a reason to reopen egress.

`build-egress` applies to pods in `lw-poc-build`. Image pulls the kubelet makes on the node, including Task step images and some BuildConfig strategy pulls, are outside that NetworkPolicy. The prefetch Task image (`registry.access.redhat.com/ubi9/openjdk-21`) can still land after this page. The ImageStream import from 4.1 is what keeps the Dockerfile `FROM` internal. A Task step that pulled from `registry.access.redhat.com` is not a reason to add `registry.redhat.io` to the allow-list.

== Key takeaways

* Build egress and application egress are different policies, on different namespaces.
* After this tighten, clone and Maven use in-cluster Service URLs. That includes Lightwell Network GAVs and Premier GAVs.
* Fulcio, Rekor, and TUF use the `*_internal_url` values from `demo-userinfo-rhtas`. The runtime `FROM` is already the internal ImageStream from 4.1.
* `build-egress` is pod egress. A kubelet pull of a Task image can still reach `registry.access.redhat.com`.
