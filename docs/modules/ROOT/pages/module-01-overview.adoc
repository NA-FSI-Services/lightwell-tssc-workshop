= Module 1: AI vulnerability storm and Lightwell Network overview
:source-highlighter: rouge
:toc:
:toclevels: 2

Attackers and researchers alike now use AI to discover and weaponize vulnerabilities faster than traditional patch cycles. Development teams feel that pressure as dependency CVEs land against libraries they cannot casually upgrade in production.

*Lightwell Network* gives you two complementary Maven (and related) streams so you can keep shipping without inventing fictional “untrusted vs secured” channels: *Validated* for active development, and *Remediated* for exact-version security backports (`.rhlw-*`).

In this module you map those tiers, the supply-chain metadata that travels with artifacts (SLSA L3, SBOM, OSV), and where the Lightwell console fits—before you wire Maven and pipelines in later labs.

== Learning objectives

By the end of this module, you will be able to:

* Explain **Validated** vs **Remediated** Lightwell Network tiers and when to use each
* Recognize remediated version suffixes such as `5.3.18.rhlw-00003` (not custom `-lw01` names)
* Describe how *SBOM*, *SLSA Level 3* provenance, and *OSV* records support triage
* Locate the conceptual Lightwell console and the canonical package remotes used in this workshop

== Background: the vulnerability storm

Modern applications pull hundreds of open source components. When a critical CVE hits a widely pinned library:

* *Major upgrades* can break APIs and delay releases
* *Doing nothing* leaves production exposed
* *Lightwell Remediated* keeps the *same upstream version line* and publishes a rebuilt artifact with a sequential `.rhlw-0000X` suffix that carries the security fix

AI accelerates both discovery of issues and the need for a repeatable remediation loop (OSV → pin → rebuild), which you practice in Module 3.

== Lightwell Network tiers (authoritative)

[IMPORTANT]
====
Use only these tier names in labs and production conversations: *Validated*, *Remediated*, and Java *OSV* (remediated).
Do *not* invent aliases such as `upstream-untrusted` or `lightwell-network-secured`.
====

[cols="1,2,2",options="header"]
|===
|Tier |Purpose |Canonical Java remote

|*Validated*
|Upstream-parity rebuilds of current libraries; typically no app code changes
|{java-validated-url}

|*Remediated*
|Exact-version backports for pinned production dependencies
|{java-remediated-url}

|*OSV (Java)*
|Machine-readable fixed-vuln records for the remediated stream (`fixed` → `.rhlw-*`)
|{java-osv-url}
|===

image::module-01-validated-vs-remediated.svg[Validated vs Remediated vs OSV tiers,width=700]

Example remediated coordinate style:

[source,text]
----
org.springframework:spring-core:5.3.18.rhlw-00003
----

Artifacts are expected to ship with supply-chain metadata:

* *SBOM* — Java CycloneDX beside the JAR (workshop uses `syft` → RHTPA in Module 4)
* *SLSA Level 3* — build provenance / signed binaries (Sigstore family; RHTAS in Module 5)
* *OSV* — fixed-version events for remediated Java (Module 3 toolkit under `tools/osv-eval/`)

== Exercise 1: Confirm the channel map in the cluster

The workshop artifact manager chart documents the same tier names even when content is *seeded* for RHDP instead of live-proxied.

. In the Showroom terminal, inspect the Lightwell channels ConfigMap (present when `lightwell-repo` is synced):
+
[source,bash,role=execute]
----
oc -n lightwell-repo get configmap lightwell-channels -o yaml
----
+
If the namespace is not ready yet, read the documented remotes from this page and continue—the names must still match *Validated* / *Remediated* / *OSV*.

. List keys and confirm mode (`seeded` or `proxy`):
+
[source,bash,role=execute]
----
oc -n lightwell-repo get configmap lightwell-channels -o jsonpath='{.data.mode}{"\n"}'
oc -n lightwell-repo get configmap lightwell-channels -o jsonpath='{.data.channels\.yaml}' | head -40
----

. Expected outcomes:
* Channel keys refer to `lightwell-java-validated`, `lightwell-java-remediated`, and `lightwell-osv-java-remediated`
* Remediated note mentions `.rhlw-0000X`
* Canonical remotes point at `packages.redhat.com/lightwell/...` (even in seeded mode)

== Exercise 2: Inspect a sample OSV `fixed` event

OSV records tell you *which* exact remediated version to pin.

. Prefer the in-cluster sample (seeded with the artifact manager):
+
[source,bash,role=execute]
----
oc -n lightwell-repo get configmap lightwell-sample-osv \
  -o jsonpath='{.data.LW-DEMO-0001\.json}' | head -60
----

. Or, from the GitOps checkout used by content authors / instructors:
+
[source,bash,role=execute]
----
# When the repo is available in your terminal workspace:
jq '.affected[0].ranges[0].events' tools/osv-eval/samples/LW-DEMO-0001.json
----

. Confirm you see a Maven ecosystem event with:
+
[source,json]
----
{ "fixed": "5.3.18.rhlw-00003" }
----

That `fixed` value is the production pin shape you will apply in Module 3—not a made-up `-lw01` suffix.
