= Module 2: Enterprise integration (Maven + artifact manager)
:source-highlighter: rouge
:toc:
:toclevels: 2

Field Lightwell Network delivery almost always puts an *enterprise artifact manager* (Nexus or Artifactory) between developers and `packages.redhat.com`. Customers integrate by pointing existing build tools and repository proxies at Red Hat secured registries; dependency manifests (for example `pom.xml`) plus Maven profiles route requests to *Validated* or *Remediated* repositories.

In this module you wire that pattern on the workshop cluster: extract `settings.xml`, authenticate with env-backed service-account placeholders (never Git), resolve Validated content, and understand how the same profiles work when remotes point *directly* at Lightwell Network.

== Learning objectives

By the end of this module, you will be able to:

* Contrast **direct** Lightwell remotes with the **proxied enterprise manager** pattern used in PoV delivery
* Run two Maven experiments against workshop Nexus: **resolution** (`dependency:get`) and **consumption** (`clean verify`)
* Use `mvn -s settings.xml -Plightwell-validated …` (and Remediated pins) against the workshop Nexus
* Explain how `LW_USERNAME` / `LW_PASSWORD` (and RHDP secret injection) supply auth without committing secrets
* Locate the Spring Boot PoC / RHDH template settings that match this lab

== Enterprise consumption patterns

[cols="1,2,2",options="header"]
|===
|Pattern |Maven remotes |When you use it

|*Direct*
|`{java-validated-url}` and `{java-remediated-url}`
|Laptop PoC or CI with Lightwell membership; auth via registry service account

|*Proxied (enterprise)*
|Internal Nexus / Artifactory repos that remote or host the same tiers
|Nearly all customer PoVs; workshop default via `charts/components/lightwell-repo`

|*Seeded (RHDP)*
|Same Nexus *repository names*; content uploaded by Job `lightwell-repo-seed`
|Deterministic labs when live LWN membership is unavailable
|===

Disconnected / air-gapped environments use the same *proxy or mirror* techniques customers already use for Red Hat content—sync into a local registry manager, then point Maven at that manager. Lightwell content is *not* synced through Red Hat Satellite content views or errata; delivery is via the artifact repository infrastructure (`packages.redhat.com` / Pulp) that build tools and managers consume.

Technology-relevant *source archives* ship in the same repositories as the binaries (standard Maven layout). Red Hat runs upstream test suites and regression checks before publish; *your* unit, integration, and performance testing in the application context remains your responsibility—patches are intended to be surgical security-only fixes.

Canonical remotes (document even when mirroring):

* Validated: `{java-validated-url}`
* Remediated: `{java-remediated-url}`
* OSV (Java): `{java-osv-url}`

[IMPORTANT]
====
Tier and profile names stay *Validated* / *Remediated* (Maven profiles `lightwell-validated` / `lightwell-remediated`).
Do *not* invent aliases such as `upstream-untrusted` or `lightwell-network-secured`.
====

== Auth: service account via env / RHDP secrets

Lightwell Network and (optionally) Nexus expect credentials. Workshop templates read them from the environment—**never** from committed files.

[source,bash,role=execute]
----
# Pattern only — do not paste real tokens into chat, Git, or screenshots
export LW_USERNAME='<registry-service-account-name>'
export LW_PASSWORD='<token>'
----

On OpenShift (proxy mode), the chart expects Secret `lightwell-network-credentials` in namespace `lightwell-repo`:

[source,bash]
----
oc -n lightwell-repo create secret generic lightwell-network-credentials \
  --from-literal=LW_USERNAME='<registry-sa|name>' \
  --from-literal=LW_PASSWORD='<token>' \
  --dry-run=client -o yaml | oc apply -f -
----

RHDP catalog delivery should inject these via platform secrets / ExternalSecret—not by editing Git values with real passwords.

Maven `settings.xml` in the Spring Boot PoC and RHDH `lightwell-java-service` skeleton binds server credentials with:

[source,xml]
----
<username>${env.LW_USERNAME}</username>
<password>${env.LW_PASSWORD}</password>
----

Set the Nexus base used by those files:

[source,bash,role=execute]
----
export LIGHTWELL_NEXUS_URL="https://$(oc -n lightwell-repo get route nexus -o jsonpath='{.spec.host}')"
echo "$LIGHTWELL_NEXUS_URL"
----

[NOTE]
====
Seeded mode may not require `LW_*` for Maven resolution against hosted Nexus repos. Still practice the env-var pattern so field delivery matches production LWN / proxy mode.
====

== Maven `settings.xml` profiles

ConfigMap `lightwell-maven-settings` (chart `lightwell-repo`) ships the learner profiles:

[cols="1,1,2",options="header"]
|===
|Profile |Repository id |Purpose

|`lightwell-validated`
|`lightwell-java-validated`
|Active development / upstream-parity

|`lightwell-remediated`
|`lightwell-java-remediated`
|Exact-version `.rhlw-*` resolution
|===

The Spring Boot PoC adds a *POM* profile `lightwell-remediated-pins` that flips dependency versions (for example `commons-lang3` → `3.14.0.rhlw-00001`). Settings profiles select *where* Maven looks; POM profiles select *which version* to build.

=== Extract settings from the cluster

. Confirm the artifact manager namespace is present:
+
[source,bash,role=execute]
----
oc -n lightwell-repo get configmap lightwell-maven-settings lightwell-channels
----

. Extract `settings.xml` into your working directory:
+
[source,bash,role=execute]
----
oc -n lightwell-repo extract configmap/lightwell-maven-settings \
  --keys=settings.xml --to=. --confirm
head -40 settings.xml
----

. Confirm channel mode (`seeded` or `proxy`):
+
[source,bash,role=execute]
----
oc -n lightwell-repo get configmap lightwell-channels -o jsonpath='{.data.mode}{"\n"}'

== Seeded content: two experiments

In *seeded* mode the Job uploads **two kinds** of Maven content into the same Nexus repo names customers would use for live LWN:

[cols="1,2,2",options="header"]
|===
|Experiment |What is seeded |What you prove

|*A — Resolution*
|`spring-core:5.3.18` and `5.3.18.rhlw-00003` as *manifest-only stubs*
|Maven can fetch Lightwell-shaped coordinates from the enterprise manager (`dependency:get`)

|*B — Consumption*
|`commons-lang3:3.14.0` and `3.14.0.rhlw-00001` as a *compile-capable* Apache Commons Lang binary (ASL 2.0)

== Exercise 2: Validated stream (resolution + consumption)

Use the workshop Spring Boot PoC sources when available on the cluster or in your GitOps checkout:

`charts/components/spring-boot-lw-poc/app/`

. Export `LIGHTWELL_NEXUS_URL` (see Auth section). For ConfigMap-extracted settings that already embed the Nexus URL, you can skip the env var.
+
[source,bash,role=execute]
----
# Prefer the app copy that already has env-aware settings.xml
cd charts/components/spring-boot-lw-poc/app

export LIGHTWELL_NEXUS_URL="https://$(oc -n lightwell-repo get route nexus -o jsonpath='{.spec.host}')"
----

=== Experiment A — resolve a Validated GAV

Prove Nexus serves the seeded Validated coordinate (watch for `Downloading from lightwell-java-validated`):

[source,bash,role=execute]
----
mvn -s settings.xml dependency:get \
  -Dartifact=org.springframework:spring-core:5.3.18 \
  -Plightwell-validated
----

Expected: `BUILD SUCCESS` with download from `lightwell-java-validated` (stub JAR is enough for this step).

=== Experiment B — build the PoC from Validated

[source,bash,role=execute]
----
mvn -s settings.xml -Plightwell-validated clean verify
----

Expected outcomes:

* `commons-lang3:3.14.0` downloads from `lightwell-java-validated` (compile-capable seed)
* Other Spring Boot deps may still fall back to Maven Central
* `BUILD SUCCESS` (tests pass)

[TIP]
====
If `mvn` is not on the Showroom PATH, use a Maven container or the toolchain documented for your RHDP environment—keep the same `-s settings.xml -Plightwell-validated` flags.
====

== Exercise 3: Remediated stream (resolution + consumption)

You are not changing production pins yet (that is Module 3). First confirm the Remediated remote serves the workshop example artifact, then build with the PoC pin profile.

=== Experiment A — resolve a `.rhlw-*` GAV

[source,bash,role=execute]
----
mvn -s settings.xml dependency:get \
  -Dartifact=org.springframework:spring-core:5.3.18.rhlw-00003 \
  -Plightwell-remediated
----

Expected: download from `lightwell-java-remediated` (resolution stub).

=== Experiment B — build with Remediated pins

This combination selects the Remediated *repository* and the POM pin `3.14.0.rhlw-00001` for `commons-lang3`:

[source,bash,role=execute]
----
mvn -s settings.xml \
  -Plightwell-remediated,lightwell-remediated-pins \
  clean verify
----

Expected: `commons-lang3:3.14.0.rhlw-00001` resolves from Nexus and `BUILD SUCCESS`.

Optional contrast — fetch the remediated pin from Nexus (exists only under `.rhlw-*`, not on Central):

[source,bash,role=execute]
----
mvn -s settings.xml dependency:get \
  -Dartifact=org.apache.commons:commons-lang3:3.14.0.rhlw-00001 \
  -Plightwell-remediated
----

Expect `Downloaded from lightwell-java-remediated`. The same GAV is absent from Maven Central.

== Direct `packages.redhat.com` pattern (field reference)

When an enterprise manager is not yet available, profiles can point straight at Lightwell Network. Shape (do not commit filled-in passwords):

[source,xml]
----
<repository>
  <id>lightwell-java-validated</id>
  <url>https://packages.redhat.com/lightwell/java/validated</url>
</repository>
<repository>
  <id>lightwell-java-remediated</id>
  <url>https://packages.redhat.com/lightwell/java/remediated</url>
</repository>
----

Pair those `<id>` values with `<server>` entries that use `${env.LW_USERNAME}` / `${env.LW_PASSWORD}` from a Red Hat terms-based registry service account.

In the field, prefer *proxied* remotes so developers never embed LWN credentials in every laptop `settings.xml`—the manager holds the remote auth once.

Artifactory uses the same remote URLs and `.rhlw-*` naming; this workshop uses Nexus as the RHDP stand-in. See the Lightwell Network “configure Artifactory” documentation for the production mirror of this pattern.

== Module summary

**What you accomplished**

* Mapped direct LWN remotes vs enterprise Nexus proxy / seeded mirrors

* Ran *resolution* (`dependency:get` on `spring-core` stubs) and *consumption* (`clean verify` with compile-capable `commons-lang3`) on both Validated and Remediated streams

**Key takeaways**

* Learner UX: `mvn -s settings.xml -Plightwell-validated …`
* Seeded RHDP can teach both GAV/remote proofs and real builds without live LWN membership
* Proxied PoV is the default enterprise story; air-gap uses mirror/proxy, not Satellite
* Credentials stay in env / RHDP secrets / cluster Secrets—never in the GitOps repo
* Source jars accompany binaries; application-context testing stays with the consumer
